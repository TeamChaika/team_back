# Восстановление пароля через привязанный Telegram

Вход → «Забыли пароль?» → существующий Telegram-бот → подтверждение → ссылка
`/reset-password#token=…` → новый пароль (8–128 символов) → обычный вход.
Email, текущий пароль и идентификатор аккаунта в этом сценарии не принимаются.

## Контракт

- `GET /api/auth/recovery/telegram` → `{url}` с `https://t.me/<bot>?start=recover`.
- `/start recover` показывает кнопку `recovery_confirm`. Только личный чат;
  числовые `from.id` и `chat.id` должны совпасть. Username не является идентичностью.
- Подтверждение ищет ровно одну существующую привязку; неоднозначные, отключённые,
  непривязанные профили отклоняются. Права складов/разделов не меняются.
- `POST /api/auth/recovery/reset`: `{token,new_password}`; строгий Origin,
  лимиты IP и хеша токена, неизвестные поля запрещены. Успех `{status:"ok"}`
  удаляет обе auth-cookie и не создаёт сессию. Все API-ответы `no-store`.
- 400: истёкший/использованный токен либо изменившаяся привязка; нужна новая ссылка.
  422: неверный формат, токен не расходуется. 429: лимит, токен не расходуется.
  503 после отправки запроса Auth: результат может быть неизвестен; сначала
  попробовать новый пароль, затем новую ссылку через 10 минут. Автоповтора PUT нет.

## Границы безопасности

Токен: 32 случайных байта, срок 10 минут, в БД только SHA-256. Он находится
во fragment URL, поэтому не попадает в HTTP access log/Referer. Frontend должен
сразу удалить fragment из адресной строки и хранить токен только в памяти.
Бот отправляет ссылку напрямую; durable inbox дополнительно удаляет credential
из пересланных/цитируемых сообщений. Содержимое Auth-ответов и секреты не логируются.

Перед PUT токен атомарно и необратимо помечается использованным. Затем снова
проверяются активность, numeric Telegram ID, portal ID и revision под блокировкой
привязки. Параллельное потребление имеет одного победителя. Новая выдача ограничена
одним разом в минуту; после расходования новая ссылка недоступна до окончания
10-минутного срока старой, чтобы не перекрыть неопределённую операцию.

Auth обновляется через существующий server-only `CHAIKA_WEB_AUTH_ADMIN_KEY`:
`PUT /auth/v1/admin/users/<bound-id>` с единственным полем `password`.
Supabase Auth `adminUserUpdate` вызывает `UpdatePassword(tx,nil)`, который удаляет
все сессии в той же транзакции. Портал проверяет каждый bearer через `GET /user`,
отклоняющий удалённый `session_id`. Это нужно подтвердить на фактической версии
Auth изолированным тестовым аккаунтом перед выпуском; unit mocks не являются
доказательством production revocation.

Флаг `password_change_required` снимается только после ответа Auth с HTTP 200
и совпадающим ID. При ошибке завершения в БД новый пароль уже может быть сохранён;
ответ сообщает это и предлагает обычный вход с завершением обязательной смены.

## Выпуск и проверки

1. Применить `migrations/documents/0003_password_recovery.sql` от migrator.
2. Проверить HTTPS `CHAIKA_DOCUMENTS_DASHBOARD_URL`, существующие bot token/username
   и admin key (никогда не печатать значения в отчёт).
3. Выпустить backend, frontend и отдельно действующий documents worker.
4. Выполнить synthetic reset: старый пароль, старый access token и refresh token
   должны быть отклонены; новый пароль работает; повтор токена не работает.
5. Проверить настоящую цепочку Telegram на специально согласованном тестовом
   аккаунте. Нельзя использовать реальные пользовательские привязки как тест.

Регрессии: `tests/test_password_recovery.py`, `test_telegram_link.py`, `test_profile.py`.
Для DB-тестов заданный `CHAIKA_DOCUMENTS_TEST_DSN` обязан быть loopback;
фикстура использует отдельную disposable БД `telegram_profile_tests`.

Откат к предыдущим образам backend/frontend/worker не требует удаления таблицы.

## Tenant runtime (09.10.2026, локально)

Полный tenant portal использует существующий профиль документов и одноразовую ссылку своего Telegram. `RESTCONTROL_TENANT_DOCUMENTS_BOT_TOKEN`, `BOT_USERNAME` и `WORKER_ENABLED=true` должны быть заданы явно через настройки компании; без них подключение и восстановление недоступны. Название бота не ищется через Chaika/config fallback. Дочерний процесс не получает Supabase admin key: `/api/auth/recovery/reset` передаёт token/password через private company capability центральному CompanyAccounts. Центральный обработчик проверяет существующую привязку, active profile, exclusive active company membership, отсутствие platform/shared identity, consumes proof до Auth, держит binding/profile/member locks и отзывает сессии. Неизвестный ответ Auth не разрешает повторное применение proof.

Публичные страницы открываются только после подтверждённого full tenant context. GET `/api/auth/recovery/telegram` и POST `/api/auth/recovery/reset` требуют точный frontend Origin своей компании; user session не требуется. Пароль не создаёт новую сессию. Это локальные проверки с fake Auth/Telegram и изолированной PostgreSQL; доставку сообщений, реальный сброс и production release они не подтверждают.

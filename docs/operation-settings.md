# Синхронизация заведений и рабочие склады

«Управление → Синхронизация и склады» доступно администратору портала, руководителю своей SaaS-компании и владельцу сервиса в контексте компании.

- `GET/POST /api/management/operation-settings`: весь каталог и три независимых выбора: `sync.department_ids`, `writeoff.store_ids`, `waybill.store_ids`.
- `mode=all` и пустой массив включает будущие элементы; `mode=selected` и пустой массив отключает всё. Это настройки операций, а не права пользователя. Нельзя передать ID другой компании или неизвестный ID.
- Данные хранятся в собственной analytics-схеме: `operation_settings`, журнал `operation_settings_audit`. Оптимистическая revision защищает от перезаписи чужой формы (409); изменение sync во время обмена отклоняется с423, черновик остаётся в форме. Сохранение само не запускает iiko.
- Для нового/скопированного списания или перемещения сервер проверяет рабочий список и прежние grants. В `options` добавлены `create_stores/create_recipients`; исторические `stores/recipients` остаются для просмотра, изменения и согласования старых документов.
- Отключение заведения останавливает публикацию новых данных, включая ручные и фоновые загрузчики. Общие справочники сети продолжают обновляться. Если Chain не умеет ограничить общий поток, неизменяемый RAW может содержать записи выключенной точки, но они не публикуются в её бизнес-данные. История не удаляется.
- Прямой OLAP также проверяет выбор до чтения кэша и под блокировкой перед запросом. Смешанный «Обзор»/«Продажи» с выключенной точкой использует сохранённые данные без live overlay. Прямые показатели/складские SALES с выключенной точкой требуют выбрать активные заведения (423); частичная сумма не выдаётся за полный итог. Старые сохранённые детализации доступны.
- Снимки, сохранённые до выключения, сохраняют исходные время и происхождение. Повторное включение разрешает последующие обновления, включая исторические периоды по действующему расписанию.

## Исходники и тесты

`app/operation_settings.py`, `app/web/operation_settings.py` — хранение/API; `app/sync_scope.py` — синхронизация; `app/web/sync_policy.py` — прямое чтение; `app/documents/reads.py`, `workflow.py` — новые документы.

Проверки: `test_operation_settings.py`, `test_sync_scope.py`, `test_live_sync_policy.py`, `test_native_documents.py`; SaaS дополнительно `test_operation_settings_tenants.py`, `test_sync_scope_tenants.py`. Использовать только одноразовую loopback БД.

## Порядок выпуска

Сначала analytics-миграция `20261016123000_operation_settings.sql`, затем documents/0011, затем backend/worker и frontend. SaaS использует отдельную tenant-миграцию из manifest с собственной runtime-ролью. Миграция не назначает выбор: отсутствие строки означает прежний режим all. Отсутствие таблицы — ошибка, не обход настройки.

После включения ограничений не откатывать backend к версии, игнорирующей эти настройки: такой откат возобновит загрузки. Для безопасного отката сначала остановить синхронизаторы, оставить добавленные таблицы и развернуть исправленную совместимую версию. Откат не удаляет бизнес-данные.

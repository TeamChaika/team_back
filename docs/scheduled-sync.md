# Синхронизации и продажи за сегодня

Перед включением примените миграцию `20260915123000_scheduled_sync.sql`.
В окружении backend задайте `CHAIKA_SYNC_ENABLED=true`, реквизиты `CHAIKA_IIKO_*`
и `CHAIKA_IIKO_CONNECTIONS_JSON` с шестью RMS. Также нужен `CHAIKA_SYNC_API_KEY`:
служебный ключ доступа к выгрузке событий и справочников через внутренний API.
JSON имеет тот же формат, что и
`config/iiko-connections.example.json`; имеет приоритет над файлом. Рабочие значения
хранятся только в защищённых переменных Timeweb.

`python -m app.serve` запускает портал и отдельный процесс планировщика.
Планировщик поднимает технический API на **127.0.0.1:8010**, не на публичном интерфейсе.
Публичным остаётся только порт `PORT`. При остановке портала завершаются и фоновые процессы.
При сбое планировщик перезапускается; PostgreSQL хранит выполненные временные слоты
и не позволяет второму экземпляру одновременно выполнять те же задачи.

## Расписание (Крым, UTC+3)

| Данные | Запуск |
| --- | --- |
| Продажи за вчера | 06:00 |
| Повторная загрузка продаж за 60 завершённых дней | 02:00 |
| Накладные, списания, перемещения за вчера и сегодня | Каждый час, :10 |
| События RMS: пропущенные дни за неделю и незавершённый текущий день | Каждый час, :20 |
| Остатки на складах | Каждый час, :30 |
| Повторная загрузка документов за открытые 60 дней | 03:00 |
| Структура, сотрудники, должности, справочники и счета | 04:30 |
| Номенклатура и техкарты | 05:00 |
| Кассовые смены за 60 завершённых дней | 06:30 |
| Денежные балансы | 07:00 |

Запуски последовательные. Занятый источник или ошибка приводят к повтору через 5 минут.
При старте выполняются последние пропущенные слоты; длинные задачи могут сдвинуть
следующую загрузку. Статусы доступны владельцу в разделе сайта «Статус загрузок».
Источники iiko читаются последовательно под общей блокировкой; каждый сохранённый день
фиксируется транзакционно. Пакеты OLAP ограничены семью днями.

## Сегодняшние показатели

`CHAIKA_LIVE_SALES_ENABLED=true` включает прямое чтение iiko для «Обзора» и «Продаж»,
если выбранный период включает сегодня. Остальные дни читаются из Supabase.
Текущая дата определяется по часовому поясу Крыма. Текущий срез заменяет сохранённые
строки сегодняшнего дня, поэтому задвоения нет. Права по ресторанам применяются
после получения общего среза и до выдачи ответа пользователю.

`CHAIKA_LIVE_SALES_CACHE_SECONDS=300` — пять минут; допустимо от 300 до 600 секунд.
Один кеш на процесс обслуживает всех пользователей, страницы и семь разрезов OLAP.
Одновременные запросы объединяются в одно последовательное получение среза.
Кнопка «Обновить» не обходит этот кеш. После перезапуска кеш прогревается перед
запуском синхронизаций. Стандартный `app.serve` использует один web worker.

При недоступности iiko допускается последний срез того же дня не старше 20 минут
с явной пометкой и временем получения. Вчерашние данные за сегодня не выдаются.
Незавершённый день не сохраняется как окончательный дневной отчёт. Детализация
сегодняшних скидок до заказов доступна после сохранения дневного отчёта.
График последних 30 завершённых дней и недельный эффект закупочных цен продолжают
использовать завершённые дни из Supabase.

## Ручной запуск отдельных задач

Миграция `20261004120000_manual_scheduled_sync.sql` добавляет отдельную очередь
`chaika.manual_sync_requests` и heartbeat `chaika.scheduler_runtime`. Примените её
**до обновления API и планировщика**. Обе таблицы защищены RLS: чтение, вставка и
изменение доступны только роли `chaika_backend`, без доступа anon/authenticated.

В блоке автоматической синхронизации администратор портала с доступом к разделу
«Статус данных» и ко всем заведениям может отправить любую из задач на ручной запуск.
`POST /api/status/sync/{job}/run` принимает только `{request_id: UUID}` и требует
существующую сессию и проверку Origin. Ответ 202 означает принятую запись в очередь,
а не завершённую загрузку. Идентификатор запроса позволяет безопасно проверить
результат повторного POST, не создавая новый запуск.

Ограничение — один принятый ручной запуск конкретной задачи за 10 минут для всех
пользователей вместе. Оно хранится в PostgreSQL и сохраняется после перезапуска.
Автоматический запуск не расходует ручной лимит, но текущая автоматическая или
ручная работа той же задачи запрещает ещё один запуск; ожидающий запрос также
блокирует повторный. Общая транзакционная блокировка задачи защищает проверку и
резервирование от гонок. Планировщик выполняет ручную очередь последовательно,
между автоматическими задачами, через тот же `run_job` и существующие блокировки
источников. Автоматические временные слоты и расписание не меняются. Файлы ручного
запуска находятся отдельно в `.local/sync/manual/{job}/...`.

Heartbeat обновляется каждые 10 секунд отдельным малым соединением, в том числе
во время длительной загрузки. После 45 секунд без heartbeat новые запросы
возвращают 503; уже принятая очередь сохраняется. Выполнявшиеся ручные задачи при
смене лидера становятся `failed/interrupted` и не перезапускаются автоматически.
Ожидающие задачи выполняет новый лидер. Ошибка ручной задачи сохраняется отдельно
от результата автоматического слота; новый ручной запуск возможен после лимита.

`GET /api/status` сохраняет прежние cron-поля и добавляет к каждой записи `scheduled`
поле `scheduler_available` и объект `manual`:
`can_run`, `blocked_reason`, `next_manual_run_at`, `remaining_seconds`, `state`,
`request_id`, `requested_at`, `started_at`, `finished_at`, `error_code`.
Причины блокировки: `permission`, `scheduler_unavailable`, `pending`, `running`,
`cooldown` (или null). Состояния ручной задачи: pending/running/succeeded/failed.
Остаток лимита вычисляется по времени БД. POST возвращает 409 для текущей работы
или конфликтующего request_id и 429 с Retry-After для лимита.

Изолированные проверки: `tests/test_manual_sync.py`, `tests/test_scheduler.py`.
Они проверяют очередь, параллельные запросы двух пользователей, лимит, перезапуск,
несовместимость текущих запусков, HTTP-права и Origin; реальные загрузчики не вызываются.

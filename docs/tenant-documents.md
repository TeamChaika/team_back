# Документы и коммерческие накладные компании

Существующие `app/documents` и `app/commercial_invoices` используют общий код в
отдельном runtime компании. Production Чайки сохраняет legacy-схемы, настройки,
ключи advisory locks, подписи уведомлений и формат документов.

## Подключение

`DocumentDatabase(url, runtime=TenantRuntime(...))` фиксирует компанию на весь
срок жизни пула. Без аргумента используется единственная startup-конфигурация
`load_runtime()`. Pool configure проверяет настоящий login и его DB-права через
`validate_database_runtime`; `SET ROLE` привилегированного подключения не
подходит. Каждая транзакция получает безопасно составленный
`search_path=<documents schema>,pg_catalog`.

Соединение несёт свой неизменяемый `tenant_runtime`, а
`app/documents/context.py` предоставляет проверенные SQL identifiers, часовой
пояс и namespace блокировок. Стоимости/техкарты, warehouse guards и исторические
PDF читают только собственную analytics-схему. Ни `search_path`, ни runtime
не выбираются из заголовка Host, параметра HTTP или тела документа.

Настройки tenant читаются только из явных аргументов и
`RESTCONTROL_TENANT_DOCUMENTS_<FIELD>`; глобальные `CHAIKA_DOCUMENTS_*`, `.env`
репозитория и file secrets не являются запасным источником.

Обязательные значения при включении native/worker/commercial:

- `DATABASE_URL` — собственная ограниченная DB-роль.
- `IIKO_URL`, `IIKO_LOGIN`, `IIKO_PASSWORD_HASH` — собственный HTTPS iiko,
  без credentials/query/fragment в URL и без доменного fallback Чайки.
- `DASHBOARD_URL` берётся из точного `TenantRuntime.frontend_origin`; другой
  адрес отклоняется.

Флаги `NATIVE_ENABLED`, `WORKER_ENABLED`, `COMMERCIAL_ENABLED`,
`COMMERCIAL_SUBMIT_ENABLED`, `COMMERCIAL_COUNTERPARTY_CREATE_ENABLED` сохраняют
свой смысл и по умолчанию выключены. `COMMERCIAL_SELLER_JSON`, `BOT_TOKEN`,
`BOT_USERNAME` также принадлежат компании. Пустой seller не заменяется реквизитами
Чайки. Проведение документов и внешние отправки в тестах не выполняются.

## Состояние и фоновые операции

Документы, каталог товаров/контрагентов, история, request IDs, очереди iiko,
Telegram offsets/updates/messages, восстановление пароля и привязка Telegram
хранятся в собственной documents-схеме. Кэши имени Telegram bot и коммерческого
расписания находятся на объекте собственного сервиса; кеш стоимости — на одном
расчёте. Единственный общий кеш изображений содержит только статические шрифты.
PDF/PNG создаются в памяти, общих файлов клиентских документов нет.

Leader lock worker, catalog lock, блокировки операций/профилей/контрагентов и
UUID повтора Telegram callback включают UUID компании. У одной компании
дубликат worker не получает лидерство; две компании могут работать одновременно.
Расписание каталогов, фильтры дат, оценка стоимости, payload iiko и уведомления
используют часовой пояс runtime. Tenant-уведомления/восстановление и изображения
не подписываются брендом Чайки; ссылки ведут на свой frontend.

Ограничение нагрузки на один физический iiko-сервер является дополнительным
межпроцессным механизмом сборщика; изоляция tenant advisory locks сама по себе
не служит доказательством такого rate limit.

## Глобальный автор документов

Корневой auth-слой передаёт проверенный `ActorContext` после центральной SSO-проверки.
Словарь из HTTP payload не создаёт полномочий. `documents.actors.owner_actor`
проверяет совпадение company UUID с неизменным runtime; владелец получает доступ
ко всем складам только собственной компании. Обычные сотрудники сохраняют свои
локальные профили, warehouse grants и Telegram-привязки.

Миграция `20261008190049_tenant_platform_document_actors.sql` хранит JSONB-снимок
реального глобального UUID, kind, имени и компании в документах, операциях и
истории. У владельца локальный FK равен NULL: запись в authentication_user,
userlink или membership не создаётся. `native_actor_audit` доступен runtime
только для добавления и чтения; ограничения БД отвергают чужой company UUID.
Создание, правка, согласование, отказ, отмена и приёмка сохраняют глобального
автора; фоновые результаты сохраняют снимок инициатора без повторной выдачи
ему прав. Уже согласованная неизменная отправка — отдельная durable-команда.

Для ещё не зарезервированного создания контрагента worker повторно проверяет
владельца через `CommercialInvoiceService(owner_authorizer=...)`. Bootstrap
должен передать `registry.authorize_platform_actor`; без callback либо после
отзыва platform membership операция запрещена. Снимок истории никогда не
превращается в доверенный ActorContext. Telegram продолжает работать только
через собственную проверенную привязку сотрудника, без глобального fallback.

## Проверки

`tests/test_tenant_documents.py` запускает действующие DocumentService и
CommercialInvoiceService на двух чистых baseline-схемах с ограниченными ролями.
Намеренно совпадают user/store/product UUID, числовой id накладной, номер счёта и
request UUID. Проверяются:

- создание/повтор/чтение/согласование в сохранённую очередь без сетевой отправки;
- чужой пользователь/коммерческий документ/PDF недоступен;
- свои товары/комментарии в карточке и CSV, свои реквизиты в сохранённом счёте/PDF;
- списание читает собственные пустые аналитические таблицы, стоимость остаётся
  неизвестной, а не нулевой;
- независимые worker locks, timezone `Asia/Tokyo` в iiko payload;
- настройки/бот/ключи из окружения Чайки и `.env` не наследуются.

Запуск: явный `RESTCONTROL_MIGRATIONS_TEST_DSN` одноразового localhost PostgreSQL,
затем `pytest tests/test_tenant_documents.py`. Для legacy-интеграций используется
отдельный `CHAIKA_DOCUMENTS_TEST_DSN` того же одноразового кластера. Эти проверки
не подтверждают production-выпуск, браузер, реальный iiko или Telegram.

`tests/test_tenant_owner_documents.py` проверяет владельца без локальной учётной
записи, приёмку с расхождениями, аудит, изоляцию и фоновое завершение без сети.

# Фоновый кэш показателей

Показатели вычисляет прямой SALES OLAP iiko. PostgreSQL хранит последний успешный
полный ответ, а не рассчитывает показатели из исторических продаж. Все карточки
одинаковой выборки используют один bundle: девять исходных полей, два периода,
четыре последовательных запроса (не более шести полей каждый), одна сессия iiko.
Уникальные чеки и средние не складываются по дням или заведениям.

`app/web/indicator_cache.py` хранит `chaika.indicator_cache`; перед выпуском применить
`supabase/migrations/20261019150000_indicator_cache.sql`. Только backend роль имеет
доступ. Ключ включает версию формата, источник, ревизию SyncPolicy, точные UUID
заведений/складов, оба периода и эффективные фильтры. Ограниченные склады никогда
не используют данные всего заведения. Права HTTP-запроса проверяются штатным
`Repository.scope`; worker заново проверяет представителя, раздел и точный ключ
до и после обращения к iiko. Несовпадающая область удаляется, обхода прав нет.

В lifespan production-портала запускается отдельный цикл `IndicatorService.start()`.
Он работает без посещений страницы и независимо от `sync_enabled`. Каждые пять
секунд проверяет due-записи; после успешного расчёта следующий назначается через
пять минут. При старте и раз в пять минут обновляется конечный список стандартных
выборок «сегодня/вчера»: сначала фактические scope активных пользователей с разделом
«Показатели», затем доступные им отдельные заведения, с дедупликацией и пределом
32 точных ключа. Читаются первые 256 подходящих пользователей по UUID. При большем
числе областей остальные прогреваются по первому запросу. При смене суток появляются
новые ключи; прежние перестают продлеваться и истекают через 24 часа.

Произвольная запрошенная комбинация продолжает обновляться без открытой страницы
24 часа после регистрации/продления; чтения продлевают срок не чаще раза в час.
В таблице максимум 256 записей: при заполнении удаляется старейшая неисполняемая
запись, при занятости всех записей admission возвращает 429. В очереди процесса
максимум 48 работ. Удаление просроченных записей выполняется при регистрации.
Нет бесконечного прогрева всех когда-либо выбранных комбинаций.

Worker выполняет работы последовательно через тот же executor, что и фильтры
ограниченных складов. PostgreSQL lease на 15 минут предотвращает повторный запуск
ключа несколькими процессами; публикация требует действующего токена lease.
Фактические запросы используют существующий глобальный `reference_lock`, общий
с синхронизациями. Занятый lock повторяется через пять секунд; другие ошибки —
через пять минут. Это частота попыток, а не гарантия свежих данных каждые пять минут:
длительная синхронизация, iiko или большая очередь могут задержать обновление.
Неопределённый logout сохраняет существующий quarantine сервиса: новые обращения
к iiko блокируются до штатного перезапуска/операторского разбора, автоматического
снятия по таймеру нет.

Успешный старый payload возвращается немедленно без ожидания iiko со статусом
`ready`, `stale`, `refreshing`, `refresh_error`, `next_refresh_at` и исходным
`observed_at`. Ошибка не меняет payload или время его наблюдения. Холодный ключ
возвращает `loading`/`retry_after`, включая `/api/indicators/query`; прежняя форма
успешного ответа и per-metric маршруты сохранены. Перезапуск API не теряет payload.
JSON Decimal сохраняется строкой, как и в прежнем `portal.serial`; перед выдачей
значения восстанавливаются в Decimal. Ошибки содержат только фиксированные коды.

Проверки: `tests/test_indicator_cache.py` создаёт и удаляет собственный PostgreSQL
кластер в `/tmp` (нужны `initdb`/`pg_ctl`, UTF8). Никакой переданный URL production
или TEST_DATABASE_URL не используется. Проверяются фоновый старт без HTTP,
повторное обновление, сохранение после перезапуска, мгновенная выдача старого
значения при блокировке iiko, коалесцирование карточек и процессов, неуспешное
обновление, изменение прав/policy/складов, карантин, предел записей, CAS/lease и
изоляция одинакового ключа в двух отдельных БД. Это не проверка SaaS schema rewrite.

# Приход, реализация внешнему контрагенту и счёт PDF

Проверено 07.10.2026. Реализация отдельна от `waybill`: прежние заявки перемещения с нулевой ценой не меняются. Рабочий модуль — `app/commercial_invoices`, публичный API — `/api/commercial-invoices/{purchase|sale}`. Production-импорт бизнес-документов в рамках разработки не выполнялся.

## Проверенный контракт iiko

Первичные источники (HTML/XSD прочитаны полностью):

- [Загрузка и редактирование приходной накладной](https://ru.iiko.help/article/api-documentations/zagruzka-i-redaktirovanie-prikhodnoy-nakladnoy).
- [Загрузка и редактирование расходной накладной](https://ru.iiko.help/article/api-documentations/zagruzka-i-redaktirovanie-raskhodnoy-nakladnoy).
- [Выгрузка приходных накладных](https://ru.iiko.help/article/api-documentations/vygruzka-prikhodnykh-nakladnykh), [выгрузка расходных накладных](https://ru.iiko.help/article/api-documentations/vygruzka-raskhodnykh-nakladnykh).
- [Поставщики](https://ru.iiko.help/article/api-documentations/rabota-s-postavschikami), [сотрудники](https://ru.iiko.help/article/api-documentations/rabota-s-dannymi-sotrudnikovv), [справочники](https://ru.iiko.help/article/api-documentations/spravochniki), [коды базовых типов](https://ru.iiko.help/article/api-documentations/kody-bazovykh-tipov).

Публичные XSD сохранены в `tests/fixtures/commercial_incoming.xsd`, `commercial_outgoing.xsd`, `commercial_validation_result.xsd` без изменения содержания. У статьи есть противоречия между примером и XSD: пример расхода заполняет склад в заголовке и строке одновременно, хотя описание запрещает это. Адаптер следует явному ограничению: только `defaultStoreId`, без `storeId` строк.

| Поле | Приход | Реализация |
| --- | --- | --- |
| Метод | POST `documents/import/incomingInvoice` | POST `documents/import/outgoingInvoice` |
| Корень XML | `document` | `document` |
| Порядок items | Первое поле | Последнее поле |
| Дата | `dateIncoming` = `dd.MM.yyyy`, `incomingDate` = `yyyy-MM-dd` | `dateIncoming` = ISO date-time |
| Контрагент | `supplier` | `counteragentId` |
| Склад | `defaultStore` и тот же `store` в каждой строке | Только `defaultStoreId` |
| Товар строки | `product` | `productId` |
| Единица | `amountUnit` = основная единица товара | Количество в основных единицах, без фасовки |
| Количество | `amount` и `actualAmount` | `amount` |
| Дополнительные поля | `num`, `incomingDocumentNumber` | — |
| Деньги строки | `price`, `sum`, `discountSum=0`, `vatPercent`, `vatSum` | Те же поля |
| Статус запроса | `PROCESSED` | `PROCESSED` |

`id` в обеих схемах помечен **только для чтения**: UUID сайта не передаётся как удалённый ID. Для сверки используется стабильный номер и маркер UUID/версии в комментарии, затем проверяются остальные поля документа. Нельзя принимать совпадение одного номера за доказательство.

В прочитанных 07.10.2026 экспортах приходных и расходных накладных есть состояния NEW и PROCESSED. `replication/serverType` вернул CHAIN. WADL текущего сервера подтверждает импорт и экспорт обоих типов. `/version` вернул `1` — это **не подтверждение версии продукта iiko**.

Оба импорта возвращают `documentValidationResult`: `valid`, `warning`, `documentNumber`, опциональные `otherSuggestedNumber`, `errorMessage`, `additionalInfo`. В нём нет подтверждённого удалённого ID или статуса проведения. Поэтому `valid=true` означает accepted; processed выставляется лишь после отдельного GET, проверки ID/статуса и совпадения сохранённого содержания. Непонятный ответ или прерванный POST означает unknown. Автоматического повторного POST для unknown нет.

`priceWithoutVat` расхода — только чтение. При анализе строк с положительным НДС фактический `price × amount` совпадал с валовой суммой (в обеих проверенных выгрузках); совпадений с суммой без НДС не было. Это подтверждает цену с НДС в реальной выгрузке, несмотря на неоднозначный комментарий формулы в XSD. Ручную цену без НДС адаптер переводит в цену с НДС; суммы строки и НДС остаются сохранёнными серверными значениями. Первую настоящую отправку нужно сверить обратным чтением iiko по суммам, НДС, количеству и статусу. Проверки схем и чтения подтверждают контракт, но не заменяют эту проверку импорта.

Если не передавать `vatPercent`, iiko берёт ставку из карточки товара. Поэтому отправляется явный 0 и `vatSum=0` для «Без НДС», а не отсутствие поля. Локальные `vat_rate=null` и `vat_rate="0"` различаются в документе/PDF; проверенная схема iiko передаёт их одинаковыми числовыми полями, отдельный признак «Без НДС» в ней не найден.

## Источник товаров и контрагентов

`catalogs.refresh` выполняет последовательно GET в одной лицензируемой сессии, освобождает её и публикует три кеша в одной транзакции. Ответы ограничены 64 МиБ. GET формы не обновляет каталоги. Worker обновляет их при запуске и после 06:00 Europe/Simferopol, проверки/повторы не чаще десяти минут. Старше двух дней справочник блокирует новый ввод; ошибка одного чтения сохраняет весь предыдущий комплект.

Товары: `v2/entities/products/list?includeDeleted=false&types=GOODS&types=PREPARED`; единица `mainUnit` сопоставляется по UUID с `v2/entities/list?rootType=MeasureUnit&includeDeleted=false`. Неизвестная единица не подменяется штуками. Цены из справочника не используются вместо ручной цены.

Контрагенты: действующие записи `/suppliers`, исключая `employee=true`, `representsStore=true` и заданный `representedStoreId`. В оба списка поступают **внешние контрагенты из справочника поставщиков iiko**. Это не заявляется как полный справочник покупателей. Дополнительное автоматическое создание покупателя не реализовано.


В кеше сохраняются только `id`, `name`, `taxpayerIdNumber` → `inn`, `address`, происхождение. KPP не найден в публичной схеме/фактическом XML и оставляется пустым. Телефоны, адреса почты, номера карт, СНИЛС, логины и другие кадровые поля не сохраняются. Реквизиты продавца задаются отдельно по проверенному образцу и замораживаются в редакции.

## Доступ, сохранение и проверка

Портал должен быть активен, иметь раздел invoices/outgoing и привязанный активный рабочий профиль. `commercial_invoice_grants` выдаёт view/create/edit/submit отдельно по пользователю, виду и складу; старые права waybill и владение порталом не дают этих прав. API прав администратора использует собственные version/request_id. Никаких прав миграция автоматически не назначает.

Сохранение содержит снимки товара, основной единицы, покупателя/поставщика, продавца, Decimal-строки и рассчитанные итоги. Количество — до трёх знаков, цена — до четырёх; суммы округляются до копеек HALF_UP по строке, затем суммируются. `price_includes_vat` задаётся явно. Неизвестные клиентские поля, включая готовые итоги, запрещены.

Submit сохраняет очередь, событие и неизменяемую редакцию в одной транзакции без согласования бухгалтером. Номер выдаёт PostgreSQL sequence. Строка документа блокируется на изменение; request_id привязан к автору и отпечатку команды. PDF читает сохранённый документ после проверки вида/склада и не принимает денежные поля в URL.

Синтетические тесты: `tests/test_commercial_invoices.py`, `test_commercial_database.py`, `test_commercial_catalogs.py`, `test_commercial_invoice_pdf.py`. Тесты БД создают отдельный временный кластер через необязательный dev-пакет pgserver; никогда не используют production DSN. Live-проверки выше состояли только из чтения и auth/logout; реальный импорт не проверялся.

## Включение и эксплуатация

Миграция `migrations/documents/0008_commercial_invoices.sql` добавочная; перемещения, списания и их права не меняет. Публичный API и отдельный worker должны получить одну версию кода. Настройки API/worker:

- `CHAIKA_DOCUMENTS_COMMERCIAL_ENABLED=true` — формы, черновики, PDF, отдельные права.
- `CHAIKA_DOCUMENTS_COMMERCIAL_SUBMIT_ENABLED=true` — постановка и обработка очереди iiko.
- `CHAIKA_DOCUMENTS_COMMERCIAL_SELLER_JSON` — закрытый JSON реквизитов: name, inn, kpp, address, bank_name, bic, account, correspondent_account. Реальные банковские реквизиты в Git не сохранять.

После миграции — обновление справочников `python -m app.documents.worker --refresh-catalogs`. В «Управлении → Приход и реализация» администратор отдельно назначает работнику склады и действия. Пользователь должен уже иметь доступ к соответствующему разделу dashboard и привязанный рабочий профиль.

После POST импортёр возвращает `accepted`; worker сверяет номер, дату, комментарий редакции, контрагента, склады каждой строки, количества, суммы и НДС отдельным GET. Только подтверждённый `PROCESSED` становится «Проведено». После неизвестного результата нет повторного POST: каждые пять минут выполняется только безопасная сверка. Исчезновение документа из экспорта само по себе не является разрешением повторить отправку.

Цена без НДС допускается только если пересчитанная цена с НДС при умножении на количество даёт сохранённую сумму строки до копейки. При расхождении округления отправка блокируется до указания цены с НДС.

Счёт доступен в сохранённой реализации и для проверяемой старой расходной накладной через `GET /api/commercial-invoices/existing-outgoing/{id}/pdf`. Старые документы с неясными единицами/фасовками, скидками, отсутствующим НДС или неподтверждённым внешним покупателем не преобразуются в платёжный счёт автоматически. Черновики и неподтверждённые отправки помечаются «Не для оплаты»; QR есть только у принятых/проведённых документов.

Реальные документы как проверочные не создавались. Первую фактическую отправку необходимо сверить с документом в iiko; тесты схем и GET не являются доказательством успешного бизнес-импорта.

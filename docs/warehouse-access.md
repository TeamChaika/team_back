# Единый предел доступа по складам

`warehouse_scope_mode` профиля: `all` сохраняет прежние границы разделов,
заведений и действий; `selected` допускает только явно назначенные склады.
Пустой выбранный набор означает отсутствие доступа к данным. Owner и
администратор не обходят этот предел при работе с данными.

## Контракт управления

`GET /api/management/accounts` возвращает `warehouses: [{id,name,parent_id}]`,
а у каждого пользователя — `warehouse_scope_mode` и `warehouse_ids`.
Создание/редактирование принимает пару этих полей. Режим `all` требует пустой
список; `selected` допускает пустой список. Передаются UUID складов source
`primary`; другие источники не смешиваются. Нельзя передать одно поле без
другого. При отсутствии обоих полей старый клиент сохраняет прежний предел,
а при создании нового аккаунта сохраняется совместимое значение `all`.
Изменение профиля и списка складов выполняется одной транзакцией с revision.

`GET /api/me` добавляет `warehouse_scope: {mode,warehouse_ids}` (эффективный
набор) и `warehouse_capabilities: {supported_sections,unsupported_sections}`.
Перечень возможностей описывает поддержку складской привязки; не заменяет
проверку прав на конкретное действие и не даёт права на документ.

## Разрешение Scope

`app/web/repository.py::Repository.scope` читает свежий профиль и grants.
Для выбранных складов список родителей служит навигацией. Если пользователю
уже назначены явные подразделения, они остаются дополнительной верхней
границей. Параметр `department_id` только сужает доступ и не добавляет соседние
склады. У пользователя без department grants родители выводятся из назначенных
складов; это не разрешает выдавать общий итог родительского заведения.
Циклы и неизвестные родители не предоставляют доступ. При выбранном пустом
наборе вход и собственный профиль доступны, аналитические данные — нет.

`Scope.unrestricted` обязательно false для `selected`. Исторические накладные
с неизвестным/чужим складом строки не показываются целиком; список, count и
карточка используют одну SQL-политику. Карточка повторно проверяет доступ в
repeatable-read снимке своих строк, чтобы параллельная синхронизация не
подменила склад между чтением заголовка и состава. Перемещение остаётся
доступным, если касается разрешённого склада отправителя **или** получателя;
название второй стороны не даёт отдельного доступа к её документам.

Нативные документы и коммерческие накладные сохраняют отдельные права
действий. `stores_for` возвращает пересечение прежних grants с глобальными
складами портального профиля. Это действует также для CSV/PDF, согласований
и Telegram. Прежние непривязанные рабочие профили не изменяются. Отсутствующий
или отключённый привязанный профиль не получает права. Старый HTTP-прокси
Django не поддерживает новый предел: выбранные склады требуют native runtime.
Форма документов показывает только эффективные grants; при пустом наборе также
не выдаёт получателей и причин списания. Приёмка с расхождениями проверяет, что
у отправителя сохранился согласующий с эффективным складским правом edit;
иначе возвращается 409 до изменения документа.

## Данные без привязки

Продукты общего каталога, техкарты, кассовые смены, сотрудники, события заказов,
топология, глобальный статус/запуск синхронизации и депозиты не имеют проверенной
привязки к складу. Для selected сервер возвращает 403 до чтения этих данных,
включая поиск, карточки, экспорт и команды записи. Нельзя подменять недоступный
складской показатель общим итогом заведения или нулём. Реестр поддержки задан
в `app/web/permissions.py`; warehouse-aware отчёты могут открываться только
после добавления и проверки соответствующего источника.

Неопубликованный финансовый модуль отсутствует в этом release. Перед его
подключением обязателен такой же selected guard на `/api/finance/*`, пока
данные и исторические снимки не имеют достоверной складской атрибуции.

AI history и инструменты используют hash режима, разделов, эффективных
складов/подразделений/RMS и версии политики; сокращение доступа скрывает прежние
диалоги. Инструменты перечитывают Scope перед запросом и сохранением ответа.

## Выпуск и проверки

1. Применить `supabase/migrations/20261007120000_warehouse_access.sql`.
   Существующие пользователи получают `all`; grants не переписываются.
2. Применить `migrations/documents/0010_global_warehouse_scope.sql`.
   Роль worker получает только SELECT на security-barrier view с колонками
   идентификатора, режима и складов; не получает изменение portal grants.
3. Выпустить API и отдельный documents worker с новой политикой. Только после
   обновления обоих включать интерфейс назначения selected.
4. Проверить разрешённый и чужой склад, пустой набор, mixed invoice, PDF/CSV,
   Telegram, owner, отзыв права без повторного входа и изоляцию кэша.

Откат кода на версию без складской политики при наличии selected пользователей
**расширит доступ**. До отката отключить такие аккаунты либо сохранить новую
серверную политику. Автоматически менять selected на all запрещено.

`tests/test_warehouse_access.py` проверяет реальное разрешение Scope, HTTP
обходы, сохранение прав старым клиентом и выполняет additive миграции на
одноразовом embedded PostgreSQL. Проверка реальных пользовательских документов
не используется как тестовая запись.

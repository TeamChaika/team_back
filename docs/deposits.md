# Депозиты в Chaika Team

`/api/deposits` обслуживает административный раздел dashboard. Гостевые ссылки,
создание платежей и webhook остаются в `pay.chaika.team`. Данные продолжают жить
в схеме `chaika_deposits` общего self-hosted Supabase; копии таблиц не создаются.

API проверяет Supabase-сессию из HttpOnly cookie и активный профиль
`chaika.web_users`. Затем передаёт только пользовательский Bearer-токен на
фиксированные маршруты `CHAIKA_WEB_DEPOSITS_API_URL` (по умолчанию
`https://pay.chaika.team/api/v1`). RLS сервиса депозитов ограничивает заведения.
Роль owner в dashboard сама по себе не даёт прав на депозиты. Управление
назначениями требует `app_metadata.chaika_deposits_role=admin`, проверяемого pay.
Изменения прав дополнительно проверяют Origin. Сервисные ключи не передаются.

Миграция `20260928094000_deposit_portal_role.sql` добавляет роль `deposits`.
Она разрешает вход, обновление сессии и работу с депозитами. `/api/me` возвращает
для неё только модуль deposits и пустые списки метаданных iiko; все маршруты
iiko сохраняют отдельную проверку scope и отвечают 403 для этой роли, даже при
наличии старых назначений ресторанов. Профиль создаётся для существующего
Supabase Auth user; пароль и права депозитов не меняются при создании профиля.

Маршруты: GET `/api/deposits`, `/export`, `/permissions`, `/venues`, `/creation-venues`,
`/access`, `/{uuid}`; POST `/api/deposits`, `/access/grant`, `/access/update`, `/access/revoke`.
Выгрузка содержит первые 1000 записей по применённым фильтрам и сортировке.
Список сотрудников для назначения прав включает активные профили dashboard.

Создание требует отдельного `chaika_deposits.user_venues.can_create=true` для
выбранного заведения (или такого назначения с `is_all=true`). Просмотр и роль
администратора сами по себе не разрешают создание. Upstream повторно проверяет
права, записывает `created_by` из проверенной сессии и использует `request_id`
как ключ идемпотентности. Повтор с теми же данными возвращает исходную запись;
другие данные или автор дают 409. Сумма — целые рубли, время бронирования — UTC+3.
Создание также проверяет Origin; оно не вызывает платёжного провайдера.

Перед выпуском необходимо применить миграцию сервиса pay
`migrations/20260928_staff_creation.sql` и обновить его backend. Dashboard
показывает форму только для разрешённых `/creation-venues`. Старые назначения
по умолчанию получают `can_create=false`; права включаются явно в «Доступах».

Проверки: `tests/test_deposits.py`, `tests/test_portal.py`,
`tests/test_restaurant_selection.py`. Дополнительно перед релизом проверены
реальная RLS, карточка, поиск со специальными символами, Excel, гостевой API.

Откат: вернуть предыдущие коммиты frontend/backend обычным revert. Дополнительная
роль совместима с прежней проверкой прав, однако старый backend не позволяет
deposit-only пользователям входить без ресторанов iiko. Гостевая оплата независима
от выкладки dashboard. Созданные профили и назначения можно удалить отдельно;
ограничение ролей нельзя сужать, пока существуют профили с ролью deposits.

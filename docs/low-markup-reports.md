# Ежедневный отчёт по наценке

Основной dashboard: назначения настраиваются через административный API ниже.
Администратор указывает отрицательный chat ID группы или канала для заведения
и явно включает отправку. Бот сверяет ID и название через `getChat`, права через
`getChatMember`. Для канала обязательны `administrator` и `can_post_messages=true`;
в группе сохраняются проверки участия и права отправки файлов. Команда `/chatid`
в группе возвращает её ID. Новые назначения выключены по умолчанию.

Планировщик `low_markup` запускается ежедневно в 09:00 Europe/Simferopol.
Учётная дата — предыдущий день относительно слота запуска, включая повтор после сбоя.
Используется отдельный SALES OLAP с `OpenDate.Typed`, явным `Department.Id`,
`DishId`, `DishName`, `DishSumInt`, `ProductCostBase.ProductCost`, `DishAmountInt`.
Удалённые блюда/заказы и возвраты исключены. Запрос выполняется через существующий
`collect_reports`, с общей блокировкой iiko и подтверждённым выходом из сессии.

Наценка = `(продажи до скидок − себестоимость) / себестоимость × 100`.
Порог строго `<150%`, до округления. Количество — за день; стоимость и цена
в Excel — на единицу. При разных ценах за день это средняя цена, взвешенная
по количеству. Одинаковые названия разных DishId не объединяются.
Нулевая/отсутствующая себестоимость не подменяется нулевой наценкой:
число таких блюд указано в подписи. Ошибка формата или чужая область данных
останавливает подготовку, а не превращает её в пустой успешный отчёт.

Таблицы `chaika.low_markup_destinations` и `chaika.low_markup_deliveries`
создаются миграцией `20261020170000_low_markup_reports.sql` до выпуска кода.
Назначения имеют ревизию и аудит администратора. Уникальный ключ доставки —
заведение и учётный день. Перед HTTP фиксируется `sending`; успешный ответ
Telegram сохраняет message_id и `sent` только после проверки положительного ID
сообщения, совпадения chat ID, непустого file ID и размера отправленного XLSX.
Имя файла Telegram может нормализовать, поэтому точное совпадение имени не требуется.
Неизвестный исход/прерванный `sending`
становится `unknown` без автоматической пересылки. Только явный 429 повторяется
после Retry-After. Отключённые в синхронизации заведения не запрашиваются.
Смена бота требует проверки назначения для нового bot ID.

Backend API:
- `GET /api/management/low-markup-reports`
- `POST /api/management/low-markup-reports/{department_id}`

Доступ — только администратору, запись с проверкой Origin. XLSX передаётся
непосредственно Telegram; в БД сохраняются только настройки и журнал доставки.
Содержимое названий блюд записывается строками, не формулами.

Этот выпуск относится к основному dashboard. В tenant runtime нельзя включать
его без `tenant_connect`, tenant migration и настройки бота собственного tenant.
Frontend показывает вкладку только при серверном флаге
`low_markup_reports_enabled`.


## Порядок активации основного dashboard

1. Сверить актуальный GitHub `TeamChaika/team_back`, ветку `chaikaiiko`, SHA и
   Timeweb App `254031`; не переносить незавершённые изменения соседних рабочих копий.
2. До выпуска кода применить миграцию в `chaika` и проверить владельца/права
   `chaika_backend`, RLS и отсутствие доступа у `anon`/`authenticated`. Таблицы
   создаются пустыми: это ещё не включение рассылки.
3. До включения назначений перенести подтверждённые исторические квитанции
   за 22.10.2026 в `low_markup_deliveries` (`sent`, исходные chat ID, bot ID,
   message ID, дата и заведение). Неопределённые результаты отметить `unknown`.
   Проверить отсутствие конфликтов по `(business_date,department_id)`; не заменять
   чужое состояние и не повторять отправку для устранения конфликта. Импорт и
   включение защищать общей блокировкой `chaika:low-markup-reports`, которую
   использует scheduler. При отсутствии подтверждения не включать рассылку.
4. Убедиться, что у четырёх согласованных заведений правильные `primary` UUID,
   синхронизация включена, bot ID совпадает с действующим токеном и бот может
   публиковать в каждый канал. Ливадию не включать. Не выводить токен в журнал.
5. После успешного выпуска нужного SHA проверить `GET /api/management/low-markup-reports`
   под администратором. Настройки менять через `POST` с текущей ревизией и
   корректным Origin. Включить только четыре согласованных назначения. Проверить
   ответ API и строки БД: `enabled`, `chat_id`, `bot_id`, ревизия; Ливадия выключена.
6. Проверить действующий scheduler и `CHAIKA_SYNC_ENABLED`, слот `low_markup`
   в 09:00 Europe/Simferopol. Следующий слот 24.10.2026 должен обрабатывать
   23.10.2026; повтор слота 23.10 обрабатывает 22.10 и пропускает импортированные
   `sent`/`unknown`. Не запускать реальную повторную рассылку для smoke-проверки.
7. При первом штатном слоте сверить scheduler run, строки ledger и исходные
   Telegram message/chat ID; успешный deployment отдельно не доказывает доставку.

Откат отправки: выключить четыре назначения с текущими ревизиями. Журнал доставки
сохранить, `sent`/`unknown` не удалять. Откат приложения не требует удаления таблиц.

# Первая контрольная оплата владельца

Закрытый операторский модуль `app.tenant_payments.acceptance_cli` разрывает зависимость
между первой проверенной оплатой и готовностью полного кабинета. HTTP-маршрута для
обхода готовности нет. Обычные создание депозита и гостевой `prepare` сохраняют
проверку готовности и подписки.

Перед контрольной оплатой нужны текущие пять предварительных этапов
`RuntimeRegistry.resolve_setup`, здоровый private runtime, активная возможность
`payments.create`, собственный терминал и его режим. Используется существующий
закрытый `acceptance_session_file` из операторского manifest. Центральный
`tenant_actor_session` повторно проверяет владельца, дочернюю сессию и её родительскую
сессию. Истёкшая сессия требует нового входа владельца; модуль её не продлевает.

Пример команды (значения UUID и путь подставляются оператором):

```sh
python -m app.tenant_payments.acceptance_cli --config /private/company.json create \
  --mode sandbox --terminal TERMINAL_UUID --amount-minor 100 \
  --request-id REQUEST_UUID --confirm-create
```

Режим `live` задаётся только явно и требует отдельного фактического разрешения
владельца на контрольную оплату. Сумма передаётся в копейках, кратно 100.
Команда `create` действительно обращается к провайдеру: при проверке этого изменения
использовался только синтетический провайдер, никаких sandbox/live вызовов не было.

До внешнего вызова сохраняются неизменяемые компания, версия конфигурации, владелец,
хеш сессии, терминал и его версия, депозит, ключ повтора, сумма, валюта и режим.
Намерение атомарно помечается использованным вместе с сохранением попытки оплаты.
После проверки терминала непосредственно перед POST повторяются центральная
авторизация, предварительные этапы, подписка и проверка неизменности терминала.
Повтор с тем же ключом не создаёт новый POST; новая сессия не может исполнить старое
подтверждение. Уже созданная операция сверяется действующим владельцем независимо
от доступности новых оплат, в том числе после изменения прочих настроек компании.
Такой режим только сверяет закреплённую старую попытку; исполнять старое
подтверждение создания с новой версией конфигурации нельзя.

```sh
python -m app.tenant_payments.acceptance_cli --config /private/company.json reconcile \
  --intent-id INTENT_UUID
```

CLI сначала печатает сохранённый `intent_id`, затем безопасную сводку с состоянием
и публичными `payment_url` / `qr_image` провайдера. Доступ к гостевому URL ещё не
готового кабинета для первой оплаты не требуется. Токен сессии, capability гостя,
callback token и ключ провайдера в вывод не входят. После оплаты повторите `reconcile`;
проверка ограничена существующей арендой сверки (обычно до 60 секунд).

Неопределённый POST остаётся `unknown`. Повтор не создаёт вторую операцию. Если ID
операции не был получен, автоматическая сверка не может его выдумать; состояние
остаётся неопределённым до достоверного восстановления исходной операции.

Миграция `20261009223000_tenant_payment_acceptance.sql` добавляет
`{payments}.acceptance_intents`; обычная payment-role не может менять закреплённые
поля. Критерий приёмки оператора требует проверенную оплаченную попытку, связанную
с подтверждением этой компании и текущей версией терминала. Уже доказанная оплата
сохраняет силу после изменения прочих настроек компании; новая версия терминала
требует новой приёмки. Исполнение ещё не использованного подтверждения всегда
требует исходной версии конфигурации компании.

Локальная проверка: `tests/test_payment_acceptance_postgres.py` — реальный временный
PostgreSQL с двумя компаниями, настоящие центральные сессии, синтетический provider
и private health. Покрыты отсутствие подтверждения, другой режим/терминал/компания,
запрет сотруднику, истечение/смена сессии, изменение версии, недоступные предварительные
этапы/подписка, отзыв перед POST, повтор, параллельный запуск, `unknown` после рестарта
и сохранение доказанной оплаты при смене настроек с повторной приёмкой при смене терминала. Реальная оплата остаётся отдельной
проверкой после подключения нужного терминала и явного разрешения владельца.

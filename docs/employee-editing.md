# Сотрудники: создание и редактирование

Владельцы сети могут создавать и редактировать сотрудников через публичный портал. Роль проверяется по `chaika.web_users`, изменения защищены проверкой Origin. В форме есть номер карты сотрудника и новый PIN для iikoFront. Пароль бекофиса, банковские реквизиты и настройки оплаты в форму не входят.

Перед запуском применить `20260915233000_employee_editing.sql` и `20260916001500_employee_pin_ack.sql`. Используется настроенное подключение `CHAIKA_IIKO_*` к Chain; отдельный ключ не нужен. У служебной учётной записи iiko должны быть права на изменение сотрудников.

Контракт: [Работа с данными сотрудников](https://ru.iiko.help/articles/#!api-documentations/rabota-s-dannymi-sotrudnikovv). На рабочем сервере 15.09.2026 проверены WADL и чтение по UUID. Частичное изменение — `POST employees/byId/{id}`, `application/x-www-form-urlencoded`. `PUT` полностью заменяет карточку и не используется. Новому сотруднику заранее назначается UUID.

Форма редактирования читает актуальную карточку из iiko. При сохранении проверяется её версия; отправляются только изменённые разрешённые поля. Все обращения последовательны под общей блокировкой синхронизации, с завершением сессии iiko.

Запись `employee_changes` фиксируется до POST. Один request_id не отправляется повторно. После POST читается карточка и сверяются переданные значения. Снимок и одна строка employees обновляются атомарно; другие сотрудники не помечаются отсутствующими. Контакты также включены в последующие полные синхронизации.

Если результат неизвестен, операция остаётся pending. Повторная попытка с тем же request_id выполняет только чтение. В списке сотрудников владелец видит свои неподтверждённые сохранения и может загрузить текущее состояние iiko. Несовпавшие поля отмечаются как reconciled, а не как успешно сохранённые. Если запись не найдена, операция остаётся pending до выяснения результата в iiko.

Проверки записи выполняются на изолированной PostgreSQL с имитацией iiko; тестовые сотрудники в рабочей сети не создаются. Первая реальная запись должна использовать реальные данные сотрудника.

`cardNumber` (строка, с сохранением ведущих нулей) читается из iiko только в редакторе владельца. Пустое изменённое значение снимает карту. Номер не добавляется в общий справочник сотрудников. При повторном чтении проверяется точное совпадение; изменение карты также меняет версию формы.

По XSD iiko `pinCode` доступен только для записи. Поле «Новый PIN-код» изначально пустое; пустое поле не отправляется, старый PIN остаётся прежним. Успешный HTTP-ответ на POST фиксируется отдельно как `pin_accepted`; PIN не пытаемся подтвердить через GET. В журнал записывается только факт изменения PIN, а для дедупликации используется HMAC с серверным секретом подключения. Из снимка одиночной карточки удаляются `password`, `pinCode`, `cardNumber`, фильтрация указана в метаданных снимка. Полная существующая синхронизация справочника не расширяется этими полями.

При таймауте POST результат PIN остаётся неизвестным, даже если остальные поля совпали. Повторный запрос никогда не отправляет PIN заново. «Загрузить текущие данные iiko» закрывает такую операцию со статусом `reconciled` и предупреждает, что PIN необходимо проверить в iikoFront либо задать новый. PIN не хранится в БД, не возвращается в форме или ошибках валидации.

# Обязательная смена временного пароля

Миграция `20261003150000_password_change_required.sql` добавляет к `chaika.web_users`
`password_change_required boolean NOT NULL` и `password_changed_at timestamptz`.
Существующие записи получают `false`; новые после миграции — `true`.
Повторное применение не снимает уже установленные флаги. Паролей, Auth-хэшей,
новых прав на Auth и публичных SQL-функций миграция не создаёт.

## Порядок выпуска

1. Применить миграцию перед запуском backend, который читает новые поля.
2. Развернуть backend и frontend с обязательной сменой пароля. Убедиться, что
   сервер проверяет актуальный флаг на каждом защищённом запросе, включая
   существующие сессии, и пропускает операции смены пароля и выхода.
3. Запустить отдельный привилегированный CLI сначала без `--apply`. Проверить
   `total`, `matches`, `to_flag`, `already_flagged`, `unsupported`, `missing_auth`.
4. С утверждённым числом `matches` выполнить `--apply --expect-matches N`.
5. Повторный read-only запуск должен показать `to_flag: 0` для совпавших аккаунтов.
   Проверить старую сессию помеченного тестового пользователя и смену пароля,
   а также сохранение доступа пользователя с собственным паролем.

Этот документ описывает процедуру; сам по себе он не подтверждает production-выпуск.

## Закрытое окружение оператора

Запускать из корня backend. CLI не импортируется в приложение.
Параметры соединения и пароль никогда не передаются аргументами командной строки:

- `CHAIKA_PASSWORD_BACKFILL_DSN`: прямое привилегированное PostgreSQL-соединение
  с явно указанными `host`, `port`, `dbname`. Если переменная отсутствует,
  CLI запрашивает DSN скрытым вводом. Для удалённого соединения используйте
  проверку сертификата TLS согласно настройкам вашего PostgreSQL.
- `CHAIKA_PASSWORD_BACKFILL_ALLOWED_TARGETS`: JSON-массив разрешённых строк
  `host:port/database`; обязательная точная проверка назначения. Например,
  для локального теста `["127.0.0.1:15438/password_backfill_test"]`.
- `CHAIKA_TEMPORARY_PASSWORD`: известный общий пароль из защищённого окружения;
  без переменной используется скрытый ввод. `--password-stdin` читает одну
  строку из защищённого канала, не из shell-литерала.

```sh
python tools/require_password_change.py
python tools/require_password_change.py --apply --expect-matches N
```

CLI требует SELECT/блокировку связанных `auth.users` и UPDATE флага в
`chaika.web_users`. Не выдавать эти дополнительные права пользователю web runtime.
`pgcrypto` должен быть установлен оператором заранее. Скрипт находит схему
расширения сам. Он не создаёт расширений или функций.

До запуска оператор проверяет, что аудит БД, прокси и сборщик SQL-трассировок
не записывают значения bind-параметров. CLI отключает обычное PostgreSQL
логирование statements/parameters в своей транзакции и прекращает работу,
если у привилегированной роли нет права изменить соответствующие параметры.
Внешний аудит, pgaudit и прокси этими настройками не управляются. Не включать
трассировку shell и не сохранять значения секретных переменных в истории.
Вывод и обработанные ошибки CLI содержат только агрегаты и безопасные сообщения.

## Границы и конкуренция

Проверка происходит внутри PostgreSQL через `pgcrypto.crypt`, без попыток входа,
извлечения хэшей в Python, изменения Auth-паролей, ролей, активности,
складских прав или Telegram. Учитываются и активные, и отключённые аккаунты.
Допускаются корректные bcrypt `$2a$`, `$2b$`, `$2y$` с cost 04–16;
совместимые варианты нормализуются к `$2a$`. Остальные форматы, NULL,
пустые/повреждённые хэши и более дорогие cost только считаются в `unsupported`.
Они не помечаются автоматически и требуют отдельного разбора оператором.
Временный пароль ограничен 72 UTF-8 байтами, чтобы избежать молчаливого
усечения bcrypt. Отсутствующие Auth-пользователи только считаются.

Read-only план ничего не блокирует и не изменяет. Apply блокирует связанные
Auth- и dashboard-строки до актуальной проверки пароля и записи флага в одной
транзакции. Смена Auth-пароля, которая завершилась раньше, будет учтена;
начавшаяся позже дождётся транзакции и затем сможет снять флаг через обычный
поток смены пароля. При несовпадении `matches` с просмотренным планом,
таймауте блокировки или SQL-ошибке транзакция откатывается. Повторить read-only
план и разбор причины; не обходить проверку числа совпадений.

Блокировки могут ненадолго задержать вход/изменение пользователей;
`lock_timeout=10s`, `statement_timeout=120s`. Apply подходит для разовой
операции в согласованное окно, не для регулярного web-запроса.
Флаги не сбрасывать массово при откате приложения: это откроет доступ
владельцам общего пароля. После неопределённого результата соединения повторить
read-only сверку — операция идемпотентна, но потерянный ответ не доказывает rollback.

## Тестирование

`tests/test_password_backfill.py` требует `CHAIKA_PASSWORD_BACKFILL_TEST_DSN`
или обычный `CHAIKA_TEST_DATABASE_URL` (в CI)
строго с `host=127.0.0.1 port=15438` для disposable PostgreSQL.
Тесты создают случайную отдельную БД, выполняют настоящую SQL-миграцию,
сверяют read-only/apply, повторный запуск, bcrypt-варианты, сохранение других
пользователей и доступов, безопасный вывод ошибок и конкурирующую смену пароля.
Созданная БД удаляется после каждого теста; остальные схемы/БД не изменяются.

```sh
python -m pytest -q tests/test_password_backfill.py
```
